# Communication Plan

Status: Working baseline

## Communication schedule

| Activity | Schedule | Platform | Purpose | Record owner |
|---|---|---|---|---|
| Weekly team meeting | Every Monday at 9:00 am | Microsoft Teams | Review progress, assign work, discuss blockers, update risks, and confirm priorities | Current Team Leader |
| Sprint planning | Beginning of each Sprint | Microsoft Teams and GitHub Projects | Confirm Sprint goal, selected backlog items, estimates, dependencies, and owners | Current Team Leader |
| Progress update | Before the weekly meeting and when blocked | Microsoft Teams and GitHub | Report completed work, planned work, and blockers | Each member |
| Sprint review | End of each Sprint | Microsoft Teams | Demonstrate completed work and check the Definition of Done | Current Team Leader |
| Sprint retrospective | End of each Sprint | Microsoft Teams | Review communication, workload, process, and improvements | Current Team Leader |
| Technical discussion | As required | Microsoft Teams and GitHub | Resolve architecture, API, database, interface, and integration decisions | Relevant Technical Lead |
| Urgent blocker notice | Within 24 hours of identifying the blocker | Microsoft Teams | Request support before the blocker affects the Sprint | Affected member |
| Document review | Before each assessment submission | Shared document and Microsoft Teams | Check content, references, formatting, consistency, and contribution evidence | All members |

## Meeting records

Meeting minutes will record:

1. Date and attendance
2. Progress since the previous meeting
3. Current blockers
4. Decisions
5. Assigned actions
6. Task owners
7. Due dates
8. Risk and schedule changes
9. Items for the next meeting

## Blocker process

1. The affected member reports the blocker within 24 hours.
2. The Technical Lead reviews the issue.
3. The Team Leader assigns support or changes the plan.
4. The team records the action in the backlog or GitHub issue.
5. Any schedule, scope, or risk effect is recorded.

## Team working rules

- Keep task ownership visible.
- Use internal due dates.
- Review workload during each weekly meeting.
- Use pull requests for shared changes.
- Discuss disagreements using project evidence.
- Record approved decisions.
- Retain evidence of contributions.
